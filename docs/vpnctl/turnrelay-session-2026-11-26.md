# Аварийный маршрут для VLESS. Передача работы, 25–26 ноября 2026 года

**Результат.** С Windows 11 в сети владельца VLESS через TurnRelay открыл BitFolk и TRANSIP в 3/3 попыток на каждый сервер, напрямую было 0/3. При передаче 8 МБ вниз и 4 МБ вверх медианы составили 10,63/13,08 и 11,22/11,23 Мбит/с соответственно. Без тестового туннеля — 63,96/44,26 Мбит/с. В Edge тот же ролик реально воспроизводился минуту в 480p по каждому маршруту. Тестировался собственный статический TURN и собственный выход. Сборка экспериментальная, профиль потребительского VPNRouter ещё предстоит интегрировать.

**Состояние на завершение.** Временные службы ACDN и Aruba остановлены, три тестовых серверных порта закрыты, временное правило firewall удалено. В Windows проверены удаление каталога испытания, отсутствие тестового задания Edge и слушателей на четырёх клиентских портах. Осталась проверенная экспериментальная копия EXE. Архив передачи содержит Markdown, измерения, исследования и Git bundle. Конфигурации с действующими ключами и паролями в архив не входят.

## Задача владельца

На домашней линии в России прямые подключения к части собственных VLESS-серверов перестают работать. Нужен резервный транспорт, который можно встроить в sing-box, проверить на Windows в виртуальной машине Omarchy и в дальнейшем обслуживать через существующие VPNRouter и vpnctl. Для подтверждения нужны сравнение на одном и том же VLESS-профиле, реальный прикладной ответ, восстановление, скорость и воспроизведение видео. Наличие белого списка у провайдера для этого сценария не требуется.

Требования к клиенту — один процесс, опциональная сборка, минимум зависимостей и небольшой патч к upstream. У каждого варианта должны быть понятны лицензия, требования к серверу, проверка подлинности и возможность отключения. Владелец отдельно попросил сохранить исследование Hiddify и альтернатив для следующих сессий.

## Архитектура и выбор реализации

sing-box принимает трафик из обычного inbound или TUN, применяет DNS и маршрутизацию и отправляет его в выбранный outbound или endpoint. VPNRouter (`aaa02215` на дату исследования) выбирает профиль, строит конфигурацию, управляет TUN и жизненным циклом ядра. На Android он использует libbox. Контроллер vpnctl (`c0baf6ec`) на Rust управляет серверами, конфигурациями, развёртыванием и подписками. До этой работы в форке уже были AmneziaWG в WireGuard endpoint, XHTTP, нативный DNSTT, атрибуция и ограничение полосы пользователя. В этой итерации проверен собственно transport outbound. Выдача нового профиля из подписки, его импорт через UI VPNRouter и автоматический выбор аварийного маршрута остаются задачами продуктовой интеграции. [Архитектура и backlog управления](transport-management.md)

Ветка содержит **две независимые** реализации.

| Тип и тег | Что передаёт | Как проверялся |
|---|---|---|
| `turn`, `with_turn` | Стандартные UDP-аллокации поверх TLS к управляемому TURN-серверу. Может нести штатный WireGuard endpoint. | Coturn, локальные UDP-пакеты, два ядра с WireGuard, TCP, UDP, DNS, отказы, смена интерфейса. В опыте с coturn получены 500/500 датаграмм по 1200 байт. |
| `turnrelay`, `with_turnrelay` | Аллокации на TURN-реле плюс зашифрованное соединение к своему `turnrelay-server`. Режим `exit` открывает TCP и UDP. Поверх него работает существующий VLESS. | Межоперабельность с сервером TurnRelay, Windows 11 через физический Wi-Fi Omarchy, отдельные отрицательные контроли, скорость и YouTube. |

Полевой кандидат — `romanrublev/turnrelay@4c3dc7ad19f564bf6a1e82ab53038cb85a835420`. У проекта есть Go-адаптер регистрации, но его `Start(stage)` не подходит контракту нашего ядра `Start(stage, scope)`. При первой реальной попытке неизменённый адаптер сообщил `outbound not started`. Внешний Go-модуль также требует Go 1.27, а релизный toolchain форка — 1.26.11, с другой версией Pion transport. Перенесены нужные пакеты под GPL-3.0, регистрация идёт через штатный реестр, доступ к реле — через dialer ядра. В составе поля проверены статические учётные данные, режим выхода и обязательный SHA-256 сертификата. Для звонков VK, получения временных учётных данных и WireGuard-режима внешнего TurnRelay понадобится дополнительная работа. [Граница переноса](../../protocol/turnrelay/UPSTREAM) · [Стандартный TURN](turn.md) · [Пример клиента и сборка сервера](turnrelay.md)

## Стенд, корректность и восстановление

Путь пакета из Windows — sing-box → TURN-реле ACDN → собственный DTLS-выход Aruba Cloud → выбранный сервер VLESS/REALITY → сайт. После подключения к TURN клиент использует одну и ту же конфигурацию VLESS, включая UUID, flow, SNI и ключи. Между прямой и резервной попыткой меняется только `detour`. На клиенте один процесс sing-box. Edge и curl использовались как обычные тестовые приложения.

25 ноября проверили Windows 11 x64, сборку 26200.6584, по три прямых и три резервных HTTPS-запроса к одному URL для каждого сервера. На BitFolk и TRANSIP каждый прямой запрос истёк через 12 с, через TurnRelay каждый получил HTTP 204. На Aruba три запроса прошли в каждую сторону после сверки SNI. В кэше клиента был `max.ru`, рабочий сервер использовал `avito.ru`. Для парного опыта обе стороны получили одно значение. Сравнение доказывает достижимость по альтернативному пути в этой сети. Конкретный механизм фильтрации не установлен. [Все 18 запросов, времена и SHA-256](turnrelay-windows-results.json)

Самостоятельный выход TurnRelay подтвердил одноразовый HTTP challenge и адрес источника Aruba. Неверные pin выхода и UUID VLESS не дали успешного прикладного ответа. Получены три совпадающих UDP-эхо за четыре попытки. HTTPS через системный Windows TUN с маршрутом /32 прошёл, после остановки тестовый маршрут исчез. При запрете прямого UDP от ядра к выбранному DNS-резолверу запрос `myip.opendns.com` через DNS detour вернул адрес Aruba. Это проверка конкретного IPv4-пути. Общесистемный DNS, произвольный IPv6, ICMP и длительную смену сетей этот опыт не покрывает.

Сборка до исправления могла более 180 с не обслуживать новые запросы после перезапуска реле. У финальной `.5` первый успешный новый HTTPS-запрос после рестарта зарегистрирован через **14,70 с по UDP** и **6,02 с по TCP** при неизменном PID, один опыт на каждый тип. Сторож раз в 3 с проверяет все аутентифицированные входящие кадры. Через 12 с полной тишины ранее работавшей сессии он закрывает старый пул и клиент, после чего создаёт новый идентификатор сессии. Следующая замена допускается через 24 с при повторной потере входящих данных. Открытые потоки при замене закрываются. Ранняя сборка `.4` в поле давала 9,73 с по UDP и 5,12 с по TCP, но реагировала только на probe-echo. На живом медленном TCP это могло преждевременно оборвать соединение. Для продолжения используйте испытанную `.5`. На выходе необходим исправленный `mux/server.go`, чтобы через 120 с прекращалось ожидание пакета от исчезнувшего клиента.

Проверены смена идентификатора после обрыва, закрытие старого UDP-сокета, восстановление новых соединений и очистка простаивающего серверного обработчика. Один живой TCP-поток выдержал принудительную потерю всех служебных probe-echo. Немедленный рестарт проверен тремя новыми TCP-потоками подряд в пределах 40 с, пять прогонов с race и три обычных. При раннем восстановлении входящих пакетов прежняя сессия иногда сохраняется и остаточные обработчики на выходе могут терять часть ответов. Независимый стресс-тест upstream с очередью из 200 UDP-пакетов давал тайм-ауты в обоих режимах race. Верхней гарантии времени восстановления или доставки произвольного UDP-бёрста нет. ## Скорость и прикладное видео на 26 ноября

Использовали тот же Windows EXE `.5`, Wi-Fi и исходные VLESS-профили. Для проверки скорости Windows curl последовательно обращался к `speed.cloudflare.com`. Загрузка — GET `/__down?bytes=N` со случайным параметром запроса, отдача — POST случайных байтов на `/__up`. Для туннеля использовали локальный вход `socks5h` в этом же sing-box. Контроль без туннеля запускали в Windows с отключённым прокси curl. Каждая передача использовала новое HTTPS-соединение и проверку сертификата. После одного прогрева проведено три переноса каждого размера в каждом направлении. В расчёт входят только HTTP 200, успешный код curl и точное число байтов. Пропускная способность — байты × 8 / полное время запроса / 1 000 000. Серии шли последовательно, воспроизведение с замерами скорости не пересекалось.

Значения ниже — медианы в **Мбит/с**. Для туннелей здесь два соединения, UDP до реле и DTLS до выхода. Серия 4/1 МБ прошла с лимитом сервера 12 TCP-потоков, серия 8/4 МБ — со штатным лимитом 256. Короткий запрос включает накладные расходы HTTPS, поэтому результаты для разных размеров приведены раздельно.

| Маршрут из Windows | Загрузка / отдача, 8 / 4 МБ | Загрузка / отдача, 4 / 1 МБ |
|---|---:|---:|
| Без тестового туннеля | 63,96 / 44,26 | 52,28 / 18,76 |
| TurnRelay → VLESS BitFolk | 10,63 / 13,08 | 10,41 / 7,00 |
| TurnRelay → VLESS TRANSIP | 11,22 / 11,23 | 8,05 / 4,56 |

Для запроса 16 МБ тот же публичный сервис вернул HTTP 403 во всех девяти попытках: на прямом пути и на обоих VLESS-путях. В скорость загрузки ответы с отказом не включались. Адрес отдачи при этом принимал все 4 МБ. Первоначальный диагностический запуск также исключён: PowerShell передавал одиночный URL по символам. Аргументы исправлены на массив строк, перед зачётными сериями проверены командная строка curl и размеры ответов.

Сравнение настроек ниже использует одинаковые файлы 4 МБ вниз и 1 МБ вверх. Значения при лимите 256 получены отдельной парной серией после смены режима на выходе.

| Настройки клиента, сервер BitFolk | Загрузка, Мбит/с | Отдача, Мбит/с | Лимит потоков выхода |
|---|---:|---:|---:|
| 1 × UDP, DTLS | 10,99 | 7,94 | 12 |
| 2 × UDP, DTLS | 10,41 | 7,00 | 12 |
| 4 × UDP, DTLS | 9,83 | 7,54 | 12 |

На этой линии повышение числа соединений с 1 до 4 не дало прироста загрузки. TCP до TURN с двумя соединениями дал меньшую скорость загрузки при сопоставимой отдаче. Разница DTLS и SRTP на одном выходе была небольшой. Эти результаты относятся к конкретной линии, реле, выходу и времени. Для оценки пропускной способности при одновременной работе нескольких приложений потребуется отдельная нагрузка.

## Настройки, которыми можно управлять

| Поле | Где и что оно меняет |
|---|---|
| `connections` | Число параллельных работников пула. Диапазон 1–60, при пропуске — 30. Каждому работающему соединению требуется аллокация и квота реле. Для воспроизведения базового опыта указать 2 явно. |
| `udp` | `true` (по умолчанию) — от клиента к TURN по UDP; `false` — до TURN по TCP. Через выход в обоих вариантах можно передавать TCP и UDP. |
| `mode` | `dtls` либо `srtp`, по умолчанию `srtp`. На выходе используется такой же `-mode`. Оба варианта требуют pin сертификата выхода. |
| `turn_server`, `turn_username`, `turn_password` | Адрес и учётная запись TURN-реле. Можно выбирать другое доступное реле, сохранив совместимые разрешения до выхода. Имя реле разрешается штатным dialer sing-box. |
| `server`, `server_port`, `password`, `server_fingerprint` | Числовой IP и UDP-порт **выхода**, его отдельный общий секрет и обязательный SHA-256 сертификата. Их выдаёт оператор выхода. Смена адреса, секрета или сертификата требует согласованной настройки. |
| `provider`, `server_type` | Реализована пара `static` / `exit`. Значения `vk`, `wireguard` и режим `wrap` валидатор отклоняет. |
| `bind_interface`, `domain_resolver`, `detour` | Поля обычного dialer управляют интерфейсом, разрешением имени реле и путём до него. Чтобы направить VLESS через TurnRelay, `detour` со значением тега TurnRelay указывают **в outbound VLESS**. |
| Серверные лимиты | У `turnrelay-server` параметр `-max-streams` ограничивает одновременные TCP-потоки одной сессии (штатно 256), `-dial-timeout` — ожидание соединения с назначением (10 с), `-udp-timeout` — простой UDP-ассоциации (60 с). Это другие ограничения, чем число клиентских соединений или TURN-квота. |
| Пробы, KCP/FEC и MTU | Проверка сессии 3/12 с, пауза между заменами 24 с и настройки внутреннего стека задаются кодом версии `.5`. В пользовательском JSON этой версии для них нет полей. |

Полный рабочий пример конфигурации с тестовыми адресами, команду сборки совместимого сервера и обязательный серверный патч см. в [руководстве TurnRelay](turnrelay.md). Доступность конкретного адреса реле проверяется с линии пользователя. Первый оперативный ориентир для этой сети — DTLS, UDP, 1–2 соединения и достаточная квота. Для выбора другого режима или реле полезны одинаковые нагрузки в обоих направлениях и реальное воспроизведение.

## Что делать следующей модели

1. Сначала установить, какую проблему воспроизводит пользователь: недоступность адреса TURN, отказ аутентификации, невозможность достичь выхода или VLESS, либо медленная доставка крупных данных при рабочих коротких запросах. Проверять это с клиентского интерфейса и тем же профилем. Предыдущая ошибка SNI показала, как легко смешать разные причины.
2. Если задача — включить резерв для ежедневного пользования, поднять постоянные управляемые реле и выход, настроить доверенный pin, учесть квоту TURN и TCP-потоки браузера. На этой ветке проверялся временный стенд. Постоянные VLESS-сервисы и клиентскую установку разворачивают отдельно.
3. Для стабильности провести длительный замер на реальных устройствах, IPv6 и DNS в масштабе системы, смену Wi-Fi/другой сети, работу нескольких приложений и нескольких клиентов, крупный UDP-бёрст. На Windows воспроизводить при активном окне браузера, фиксировать время до первого кадра, паузы, разрешение и медиаданные с CDN. Парные серии для настроек чередовать, указывать размеры файлов и число повторов.
4. Для продуктовой интеграции проверить ручной JSON через генератор VPNRouter, разбор подписки, диагностику и реакции существующего selector. Проверять фактический путь после изменения конфигурации: исследованный `PUT /configs` может вернуть 204 без применения нового графа. Для vpnctl нужны проверка возможностей установленного ядра, штатная валидация, откат и совместимая выдача подписок. [План по VPNRouter и vpnctl](transport-management.md)
5. Если требуется следующий принципиально иной транспорт, использовать сохранённые приоритеты и сравнить его на тех же Windows-машине, VLESS-узлах и способе приёмки. Доступ через инфраструктуру видеозвонков и через редакторы остаётся отдельной гипотезой. Сравнение на домашней линии важнее списка поддерживаемых провайдеров.

## Как повторить исходную сборку и сравнение

После получения ветки из Git bundle команды ниже выполняются из корня репозитория. Для точного EXE нужен Go 1.26.11. Подмодули должны быть инициализированы.

```bash
git submodule update --init --recursive
tags=$(sed -n 's/^  DEFAULT_TAGS: "\(.*\)"/\1/p' .github/workflows/release.yml)
GOTOOLCHAIN=go1.26.11 GOOS=windows GOARCH=amd64 CGO_ENABLED=0 \
  go build -buildvcs=false -trimpath -tags "$tags,with_turnrelay" \
  -ldflags '-s -w -checklinkname=0 -X github.com/sagernet/sing-box/constant.Version=v1.14.4-vpnctl-turnrelay.5' \
  -o sing-box-turnrelay.exe ./cmd/sing-box
sha256sum sing-box-turnrelay.exe
```

Для исходной проверки напрямую и через реле используется штатный для ветки тестовый PowerShell-скрипт. Входные объекты конфигурации содержат реальные учётные данные и создаются оператором. Скрипт передаёт объединённую конфигурацию ядру на stdin.

```powershell
.\scripts\turnrelay_windows_probe.ps1 -Core .\sing-box-turnrelay.exe `
  -VlessOutbound .\vless-outbound.json -TurnRelayOutbound .\turnrelay-outbound.json `
  -Attempts 3 -TimeoutSeconds 12
```


Для импорта комплекта в чистый клон форка можно выполнить следующие команды. Путь к bundle задаётся относительно распакованного архива. Внутри уже существующей рабочей ветки сначала сверяют её состояние.

```bash
git bundle verify /path/to/turnrelay-session.bundle
git fetch /path/to/turnrelay-session.bundle refs/heads/feat/turn-tls-research:refs/heads/turnrelay-handoff
git switch turnrelay-handoff
```

Для независимого повтора теста скорости открыть профиль с локальным mixed-входом на loopback. curl передаёт доменное имя в sing-box через SOCKS5h. На одну пару замеров ниже приходится 8 000 000 байт скачивания и 4 000 000 байт отдачи. Использовать случайное содержимое файла, отключать переменные исключения прокси для этого опыта, повторить три раза с уникальным параметром запроса. Для контроля в той же Windows запускать curl с `--noproxy '*'`. Результаты сохранять только при точном размере и HTTP 200.

```powershell
$proxy = 'socks5h://127.0.0.1:37954'
$nonce = [guid]::NewGuid().ToString('N')
curl.exe -q --proxy $proxy --noproxy unused.invalid --silent --max-time 60 -o NUL -w '%{http_code} %{size_download} %{time_total}' "https://speed.cloudflare.com/__down?bytes=8000000&nonce=$nonce"
curl.exe -q --proxy $proxy --noproxy unused.invalid --silent --max-time 60 -o NUL -w '%{http_code} %{size_upload} %{time_total}' -H 'Content-Type: application/octet-stream' --data-binary '@upload-4000000.bin' "https://speed.cloudflare.com/__up?nonce=$nonce"
```
