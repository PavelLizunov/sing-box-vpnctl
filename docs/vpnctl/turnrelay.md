# TurnRelay при недоступности прямого VLESS

TurnRelay поднимает соединение через доступное TURN-реле до собственного сервера `turnrelay-server`. В режиме `exit` сервер открывает TCP-соединения и передаёт UDP-пакеты. Обычный VLESS/REALITY можно оставить верхним протоколом и направить его соединение через outbound `turnrelay`. Получается один клиентский процесс sing-box. Прикладной ответ через VLESS проверяет всю цепочку до сайта назначения.

Использован код `romanrublev/turnrelay` на ревизии `4c3dc7ad19f564bf6a1e82ab53038cb85a835420`. Опциональный outbound `turn`, также имеющийся в этой ветке, использует стандартный TURN поверх TLS и имеет другой формат конфигурации и серверные требования. [Код и формат upstream](https://github.com/romanrublev/turnrelay/tree/4c3dc7ad19f564bf6a1e82ab53038cb85a835420/singbox) · [Стандартный TURN](turn.md)

## Серверная сторона

1. На доступном клиенту узле нужен TURN-сервер с учётной записью и возможностью создавать UDP-аллокации. Клиент может подключаться к самому TURN-серверу по UDP или TCP. На стенде реле разрешало клиенту обращаться только к IP собственного узла выхода.
2. На узле выхода используйте `turnrelay-server` указанной ревизии с локальными исправлениями по инструкции ниже. Передайте секрет через переменную окружения `TURNRELAY_PASSWORD`. Путь для сертификата должен быть доступен служебному пользователю. Пример команды запуска — `turnrelay-server -listen :53492 -mode dtls -cert /var/lib/turnrelay/exit.pem`. Сохраните SHA-256 сертификата из вывода запуска для конфигурации клиента. Разрешите этот UDP-порт со стороны реле. [Реализация сервера](https://github.com/romanrublev/turnrelay/blob/4c3dc7ad19f564bf6a1e82ab53038cb85a835420/cmd/turnrelay-server/main.go)
3. Если через этот выход будет работать VLESS, проверьте доступ с узла выхода к тому же TCP-порту VLESS и соответствие SNI и ключей REALITY серверной конфигурации. Узел выхода TurnRelay и сервер VLESS могут находиться как на одной машине, так и на разных.

Соберите сервер из корня форка на Linux с Go 1.27+. Список файлов берётся из `UPSTREAM` и включает все локальные изменения к исходникам указанной ревизии. Сервер закрывает обработчики при остановке и при простое, освобождает UDP-ассоциации закрытой сессии и ограничивает их число до 256 на сессию. [Список изменений](../../protocol/turnrelay/UPSTREAM)

```sh
set -e
core_dir="$(pwd)"
git clone https://github.com/romanrublev/turnrelay.git turnrelay-server-src
cd turnrelay-server-src
git checkout --detach 4c3dc7ad19f564bf6a1e82ab53038cb85a835420
port="$core_dir/protocol/turnrelay"
sed -n '/^Patched files:$/,/^$/s/^  //p' "$port/UPSTREAM" |
while IFS= read -r file; do
    sed 's|github.com/sagernet/sing-box/protocol/turnrelay/internal/upstream|github.com/romanrublev/turnrelay|g' \
        "$port/internal/upstream/$file" > "$file" || exit 1
done
go get github.com/pion/turn/v5@v5.1.3
CGO_ENABLED=0 go build -trimpath -ldflags='-s -w' -o turnrelay-server ./cmd/turnrelay-server
```

## Клиентская конфигурация

Релизные сборки для Linux, Windows, macOS и Android включают `with_turnrelay`. Для минимальной сборки можно опустить этот тег. Ниже приведён объект для массива `outbounds`. Адреса и учётные данные замените своими, на обоих концах выберите одинаковый `mode`. В существующем объекте VLESS укажите `"detour": "relay"`; для проверки пути без VLESS можно направить тестовый вход сразу на тег `relay`. [Сборка](build.md)

```json
{
  "type": "turnrelay",
  "tag": "relay",
  "provider": "static",
  "server_type": "exit",
  "server": "203.0.113.20",
  "server_port": 53492,
  "turn_server": "192.0.2.10:3478",
  "turn_username": "operator-issued-user",
  "turn_password": "<пароль TURN>",
  "password": "<отдельный секрет выхода>",
  "server_fingerprint": "<64 шестнадцатеричных символа SHA-256 сертификата выхода>",
  "connections": 2,
  "mode": "dtls",
  "udp": true
}
```

На сегодня зарегистрирован режим `exit` со статическими учётными данными. `udp: false` выбирает TCP на участке клиент → TURN. Верхнему протоколу доступны TCP и UDP при любом из этих значений. Проверенные на Windows конфигурации используют два соединения. Значение `connections` по умолчанию равно 2. Допустимый диапазон явных значений — от 1 до 60. В сборке есть режимы DTLS и SRTP с обязательным pin сертификата узла выхода. Для управляющего обмена с TURN-реле используются обычные UDP или TCP и long-term authentication. Само реле видит имя учётной записи, адрес выхода, объём и время передачи. Шифрование полезной нагрузки и проверка сертификата действуют между клиентом и узлом выхода. Доступ через VK, режим WireGuard из TurnRelay и получение учётных данных из ссылки на звонок этой интеграцией не предоставляются.

## Стенд и способ сравнения

25 ноября 2026 года клиентом была Windows 11 x64, сборка 26200.6584, в виртуальной машине Omarchy. Её Ethernet и сетевой мост Omarchy имели маршрут к физическому Wi-Fi. Использовались два управляемых оператором узла. На ACDN запущено статическое аутентифицированное TURN-реле, разрешающее пересылку к адресу Aruba. На Aruba работал `turnrelay-server` указанной ревизии с исправлением очистки простаивающих соединений, в режиме DTLS с сохранённым сертификатом, проверкой его SHA-256 на клиенте и отдельным секретом доступа. Выход по умолчанию запрещал доступ к приватным адресам. Для контрольного HTTP-запроса приёмник на ACDN проверял одноразовое значение и возвращал адрес источника. Проверка UDP требовала получить то же случайное значение в ответ.

Для VLESS в обеих попытках используются одни и те же сервер, порт, UUID, flow, TLS SNI, ключ REALITY, short ID и отпечаток клиента. Меняется только `detour`. На Windows скрипт по очереди открывает временный loopback-вход в том же исполняемом файле sing-box, посылает HTTPS-запрос и печатает строки JSON с кодом curl, HTTP-статусом и временем. Каждая попытка запускает ядро заново. Для указанного по умолчанию URL ожидается HTTP 204. [Скрипт сравнения](../../scripts/turnrelay_windows_probe.ps1)

```powershell
.\scripts\turnrelay_windows_probe.ps1 -Core .\sing-box.exe `
    -VlessOutbound .\vless-outbound.json -TurnRelayOutbound .\turnrelay-outbound.json
```

Пропускная способность, сравнение настроек и минутные прогоны YouTube на этой же Windows-машине проверены 26 ноября. [Отчёт для продолжения работы](turnrelay-session-2026-11-26.md) · [Показания curl и видеоплеера](turnrelay-media-results.json)

## Измерения из Windows

Критерий успеха — HTTPS-запрос к `www.gstatic.com/generate_204` вернул HTTP 204 с проверкой сертификата. Для сборки `v1.14.4-vpnctl-turnrelay.5` на каждом узле было по три прямые попытки и три через TurnRelay, порядок чередовался, лимит одной попытки — 12 секунд. На пути через реле источником был один и тот же выход Aruba. Поэтому для BitFolk и TRANSIP трафик действительно шёл дальше на их VLESS-серверы. [Все 18 результатов и SHA-256 сборки](turnrelay-windows-results.json)

| Сервер VLESS | Прямой VLESS | Тот же VLESS через TurnRelay | Время успешного запроса через реле |
|---|---:|---:|---|
| BitFolk | 0/3, тайм-аут | 3/3 | 0,91–0,98 с |
| TRANSIP | 0/3, тайм-аут | 3/3 | 1,28–1,70 с |
| Aruba с актуальным SNI | 3/3 | 3/3 | 0,84–0,89 с, напрямую 0,35–0,48 с |

В предварительной серии с лимитом в 20 одновременных TURN-аллокаций и параллельными тестами через реле прошли 2/3 попыток BitFolk и 1/3 TRANSIP. Финальная серия использовала отдельный интервал, освобождённые аллокации и лимит 96 на временном стенде. Три повтора показывают достижимость на этой линии в период проверки. Длительная стабильность требует отдельного замера.

Через TurnRelay как самостоятельный выход Windows получила HTTP-ответ с контрольным значением и ожидаемым адресом Aruba, а также три корректных UDP-эхо за четыре попытки. С подменённым pin выхода или неправильным UUID VLESS успешного прикладного ответа не было. Системный Windows TUN проверен на HTTPS-запросе с отдельным маршрутом /32. После завершения процесса этот маршрут исчез. Проверка охватывала тестовое назначение и IPv4.

Для отдельной проверки DNS ядро пересылало запрос типа A к `myip.opendns.com` через свой DNS-транспорт UDP с `detour` на TurnRelay. Правило Windows Firewall блокировало для этого процесса прямой UDP-доступ к выбранному резолверу `208.67.222.222:53`. В ответе резолвер вернул публичный адрес Aruba. Этот опыт проверяет путь одного DNS-запроса. Системный DNS для других приложений и утечки IPv6 на этой машине остаются непроверенными.

**Восстановление после отказа.** Во время успешного запроса тест приостановил процесс TURN-реле. После первого тайм-аута процесс реле был возобновлён и перезапущен с потерей всех аллокаций. Проверенный Windows-бинарник снова получил HTTP 204 через 14,70 с при подключении к реле по UDP и через 6,02 с по TCP, по одному испытанию. Процесс sing-box и его PID сохранялись. В текущей реализации отсчёт 12 с начинается при создании каждой сессии, даже если реле изначально недоступно. Полученные от аутентифицированного выхода данные и ответы на пробы обновляют таймер. При смене интерфейса близкие уведомления объединяются в окне 150 мс, затем клиент закрывает старые аллокации и переходит на новый идентификатор сессии. Уже открытые потоки и UDP-ассоциации закрываются. Новые вызовы во время перестройки ждут готовности следующего поколения в пределах срока запроса. На обоих концах таймер выпускает UDP-пакеты, оставшиеся после пропуска номера, даже если поток затих. Время полевого теста измерялось до первого успешного нового HTTPS-запроса после запуска реле. В ранней сборке без этого восстановления свежие запросы через UDP оставались без ответа более трёх минут. [Адаптер](../../protocol/turnrelay/outbound.go) · [Регрессионный тест](../../protocol/turnrelay/outbound_test.go)

**Сборка.** Для Windows/amd64 и Linux/amd64 использован Go 1.26.11, `CGO_ENABLED=0`, профиль релиза с добавленным `with_turnrelay`. На Windows исполняемый файл занимает 50 104 832 байта, при тех же флагах без `with_turnrelay` — 48 484 352 байта. Прибавка — 1 620 480 байт (3,34 %). Библиотека VK, tray и клиентские исполняемые файлы upstream в этот профиль не входят. Для исходников нового пакета и всего основного модуля с тегами релиза, `with_turn` и `with_turnrelay` на Linux инструмент `govulncheck` сообщил ноль достижимых известных уязвимостей. В полном PE с тегом и без него сканер сообщил одинаковые пять записей по символам уже имевшихся зависимостей. [Ревизия и локальные изменения](../../protocol/turnrelay/UPSTREAM)

**Память и CPU на Windows.** В каждом из трёх профилей после одного прогревочного запроса выполнили пять одинаковых HTTPS-запросов через VLESS Aruba с паузой 1 с. Средний рабочий набор процесса по пяти снимкам составил 28,19 МиБ у обычной сборки, 28,05 МиБ у экспериментальной с прямым VLESS и 33,11 МиБ при активном TurnRelay с двумя соединениями. За эти интервалы Windows начислила процессу соответственно 15,62, 0 и 171,88 мс CPU. Один короткий интервал на профиль и дискретность счётчика ограничивают точность замера CPU. [Исходные значения и длительность интервалов](turnrelay-windows-results.json)

**Платформы и регрессии.** Опциональное ядро собрано для Windows (amd64, arm64), Linux (amd64, arm64, armv7) и macOS (amd64, arm64). На Windows/amd64 проведены полевые испытания. Повторная сборка Windows из тех же исходников с `-buildvcs=false -trimpath` дала побайтово идентичный EXE. На Linux/amd64 прошли тесты 27 пакетов основного Go-модуля с релизными тегами, `with_turn` и `with_turnrelay`. Тест восстановления после потери реле проверяет смену идентификатора сессии, закрытие прежнего UDP-сокета и доставку пакета по новому пути. В другом тесте выход отбрасывает ответы на все служебные пробы, пока по одному TCP-потоку идёт обмен. Поток пережил интервал обнаружения обрыва во всех трёх прогонах с `-race`. Тест очистки на выходе проверяет завершение простаивающего обработчика.

Отдельный регрессионный тест тут же запускает реле снова на том же порту и требует три новых TCP-соединения с правильным ответом подряд в течение 40 с. На loopback прошли пять повторов под `-race` и три обычных. В трёх дополнительных прогонах под `-race` сразу после перезапуска передавали также `InterfaceUpdated`. Все три прошли. Эти результаты дополняют одиночные замеры UDP и TCP в Windows. Для произвольного сбоя сети верхняя граница времени восстановления не установлена.

Для Android команда `go run -tags with_turnrelay ./cmd/internal/build_libbox -target android` собрала обе AAR с NDK r28 и OpenJDK 17. Для обычной библиотеки проверен minSdk 24, для legacy — 21. В каждой проверены целостность архива, Java-класс Libbox и теги Go в нативных библиотеках для arm64-v8a, armeabi-v7a, x86 и x86_64. Полевой запуск Android в эту серию не входил.

По окончании испытаний временные службы реле и выхода остановлены, тестовые порты закрыты. Копия проверенного клиента и скрипт сравнения сохранены в Windows в `%LOCALAPPDATA%\VPNRouter\Experiments\TurnRelay`. Для повторного подключения нужны работающее реле и выход с соответствующей конфигурацией.

## Совместимость и ограничения

Чистая регистрация `turnrelay/singbox.RegisterOutbound` из указанной ревизии компилируется с нашей базой, но первая попытка передачи на Windows завершилась ошибкой `turnrelay: outbound not started`. В upstream-адаптере метод `Start(stage)`. Менеджер нашего sing-box 1.14.4 ищет `Start(stage, scope)` и пропускает outbound, не реализующий этот интерфейс. Компиляция и разбор конфигурации не обнаруживают эту ошибку. [Lifecycle в ядре](../../adapter/lifecycle.go) · [Менеджер outbound](../../adapter/outbound/manager.go) · [Адаптер TurnRelay](https://github.com/romanrublev/turnrelay/blob/4c3dc7ad19f564bf6a1e82ab53038cb85a835420/singbox/outbound.go)

У исследованного профиля Aruba в локальном кэше клиента стоял SNI `max.ru`, на работающем сервере — `avito.ru`. Через рабочий TurnRelay профиль из кэша дошёл до проверки сертификата и получил ошибку несоответствия имени. Для парного испытания Aruba использован SNI из фактической конфигурации сервера на обоих путях. Профили BitFolk и TRANSIP проверялись с их исходным SNI.

Наблюдение на физическом интерфейсе при прямой попытке на Aruba зафиксировало TCP SYN, ответ SYN/ACK и повторную отправку клиентских данных. До тайм-аута в захвате не было ответных данных сервера. Эти результаты описывают поведение пути в момент проверки. Они не определяют конкретное правило фильтрации или оборудование провайдера.

С тестами upstream под `-race` прошли пакеты `exit`, `relay` и `obfs`. `TestPoolEchoAcrossWorkers` отправляет подряд 200 UDP-пакетов по 1000 байт через четыре worker и ожидает все 200 за 15 секунд. На этой машине в отдельном повторе тест трижды завершился тайм-аутом под `-race` и трижды без него. Это ограничивает выводы о работе под пакетной нагрузкой. Небольшой обмен с подтверждением и массовую передачу следует измерять раздельно. [Исходник теста](https://github.com/romanrublev/turnrelay/blob/4c3dc7ad19f564bf6a1e82ab53038cb85a835420/mux/pool_test.go)
